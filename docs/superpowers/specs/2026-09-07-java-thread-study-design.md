# java-thread-study 설계

작성일: 2026-09-07

## 목표

자바 스레드를 테스트로 관찰하며 배운다. 기본 구조를 먼저 손으로 만져본 뒤 가상 스레드로 넘어간다.

읽고 끝나는 예제 모음이 아니라, **한 단계씩 직접 작성하고 실행해 확인하는** 방식으로 진행한다.

## 환경

- Java 25 (Temurin 25.0.4, SDKMAN 설치. 시스템 기본 JDK는 21로 유지)
- Gradle 9.7.1 (wrapper. Java 25는 Gradle 9.1+ 필요)
- JUnit 5 + AssertJ

외부 동시성 라이브러리는 도입하지 않는다. 배우려는 원리가 라이브러리 뒤로 숨기 때문이다.

## 구조

```
java-thread-study/
├── README.md                        로드맵 + 진행 상황
├── build.gradle
├── docs/step0N-<주제>.md            단계별 학습 노트
└── src/test/java/study/thread/
    ├── support/                     공통 관찰 도구
    └── step0N_<주제>/               단계 하나 = 패키지 하나
```

단계 하나가 패키지 하나 + 노트 하나에 대응한다. 단계를 추가할 때 기존 것을 건드릴 필요가 없다.

`src/main`은 테스트만으로 표현하기 어려운 예제 클래스가 필요할 때만 만든다.

### support 패키지

동시성 코드는 결과만 봐서는 왜 그렇게 됐는지 알 수 없다. 그래서 실행 과정을 보여주는 도구를 둔다.

- `Timeline` — 어느 스레드가 언제 무엇을 했는지 한 줄로 출력. 가상 스레드는 `(V)`로 표시한다.
- `Sleeper` — `try-catch`가 본론을 가리지 않게 감싼 sleep. 인터럽트를 삼키지 않고 상태를 되돌린 뒤 다시 던진다.

## 커리큘럼

| 단계 | 주제 | 핵심 질문 |
|---|---|---|
| 01 | Thread / Runnable | `start()`와 `run()`은 뭐가 다른가, 왜 Runnable을 쓰나 |
| 02 | 생명주기 · interrupt | 스레드는 어떻게 끝나나, 취소는 왜 "협력"인가 |
| 03 | 공유 상태 | 경합 재현 → `synchronized` / `volatile` / `Atomic`은 각각 뭘 해결하나 |
| 04 | wait·notify · Lock | 조건 대기, `ReentrantLock`, 데드락 만들어보기 |
| 05 | ExecutorService | 스레드를 왜 직접 안 만드나, 풀 고갈은 어떻게 생기나 |
| 06 | CompletableFuture | 비동기 조합과 예외 전파, 어느 스레드에서 도나 |
| 07 | 가상 스레드 | 플랫폼 스레드와 뭐가 다른가, 캐리어·pinning, 100만 개 실험 |
| 08 | 구조적 동시성 · ScopedValue | `ThreadLocal`의 대안, preview 기능 |

01~06이 기본 구조, 07~08이 가상 스레드다.

앞 단계를 먼저 겪어야 07에서 **비교 대상**이 생긴다. 가상 스레드의 의미는
플랫폼 스레드의 한계(생성 비용, 풀 고갈, 블로킹 낭비)를 직접 부딪혀봐야 드러난다.

### Java 25를 쓰는 이유

- **JEP 491** — 가상 스레드가 `synchronized` 안에서 캐리어를 pinning하지 않는다 (Java 24 반영).
  Java 21과 비교 실험이 step07의 좋은 교보재가 된다.
- **ScopedValue** — Java 25에서 정식. step08에서 `ThreadLocal`의 대안으로 다룬다.
- **StructuredTaskScope** — Java 25에서도 여전히 preview다. step08에서 `--enable-preview`가 필요하며,
  그 시점에 build.gradle에 컴파일·실행 플래그를 추가한다.

## 테스트 원칙

동시성 테스트는 결과가 흔들린다. 성격이 다른 두 종류를 섞지 않는다.

- **검증 테스트** — 실행 순서를 못 박아 항상 같은 결과가 나오게 만든 뒤 단언한다.
  "새 스레드에서 실행됐다" 같은 사실은 실행 스레드 이름을 값으로 붙잡아 단언한다.
- **관찰 테스트** (`@Tag("observation")`) — 경합이나 순서 뒤바뀜을 일부러 드러낸다. **단언하지 않는다.**
  경합은 "가끔" 일어나는 것이 본질이라, 어느 쪽을 단언해도 거짓말이 된다.

`./gradlew test -PexcludeTags=observation`으로 검증 테스트만 돌릴 수 있다.

## 진행 방식

한 단계씩 진행한다. 각 단계에서:

1. 그 단계의 핵심 질문을 확인한다
2. 테스트를 작성해 실행하고 실제 동작을 관찰한다
3. 확인한 것을 `docs/step0N-*.md`에 정리하고, README 로드맵 체크를 채운다

설계는 고정이 아니다. 진행하다 구조가 안 맞으면 그때 바꾼다.
